## 슬라이드 4. 해시 테이블 설계 ⭐ (핵심)

**화면에 띄울 것**

**문제.** 키가 100만 개일 때 `"user:1"`을 하나씩 비교하며 찾으면 느리다 → O(n)

**아이디어.** 키를 계산식에 넣어 **"몇 번 칸에 있는지"** 를 바로 구한다.

```
해시 함수(FNV-1a): "user:1" → 1830439627
칸 번호 = 해시 & (칸 수 - 1)  → 1830439627 & 15 = 11
```

| 키 | 해시값 | 칸 번호 (16칸) |
|---|---|---|
| `user:1` | 1830439627 | 11 |
| `user:2` | 1847217246 | 14 |
| `user:3` | 1863994865 | 1 |
| `apple` | 280767167 | 15 |
| `banana` | 3649609552 | 0 |

| 설계 결정 | 이유 |
|---|---|
| FNV-1a 32bit | 짧고 빠르고 분포가 고름 |
| 칸 수는 항상 **2의 거듭제곱** | `% 칸수` 대신 비트 AND 로 계산 |
| 충돌은 **체이닝** (칸마다 연결 리스트) | 구현이 단순하고 삭제가 쉬움 |
| 적재율 0.75 초과 → **2배 확장**, 0.125 미만 → 절반 축소 | 체인이 길어지지 않게 유지 → 평균 O(1) |

```
칸 3:  [k5|값] → [k9|값] → [k20|값]    ← 같은 칸에 3개. 키 문자열을 직접 비교해 구분
```

**말할 것**
- "같은 칸에 두 키가 들어올 수 있는데, 이게 **충돌**입니다. 칸 안에 연결 리스트를 두고, 칸에 도착한 뒤 **키 문자열을 직접 비교**합니다. 그래서 충돌이 나도 값이 섞이지 않습니다."
- "그냥 두면 데이터가 늘수록 체인이 길어져 O(n)에 가까워집니다. 그래서 적재율 0.75를 넘으면 칸을 2배로 늘리고 전부 재배치합니다. 실험에서 13개를 넣자 16칸이 32칸이 됐습니다(13/16 = 0.81 > 0.75)."
- "확장 임계값(0.75)과 축소 임계값(0.125) 사이를 넓게 둔 건, 경계에서 늘렸다 줄였다 반복(thrashing)하지 않게 하려는 겁니다."
- 증거: "충돌을 강제로 만들려고 해시 함수를 주입할 수 있게 했습니다. 모든 키를 한 칸에 몰아넣어도 정상 동작하는 걸 테스트했습니다."

**예상 질문**
- *왜 개방 주소법이 아니라 체이닝인가요?* → 삭제가 단순합니다(노드 제거). 개방 주소법은 삭제 시 표식(tombstone)이 필요합니다.
- *왜 `%`가 아니라 `&`인가요?* → 칸 수가 2의 거듭제곱이면 둘이 같은 결과이고 비트 연산이 더 빠릅니다.

## 슬라이드 5. 주요 함수 동작: set / resize

**화면에 띄울 것**

```js
set(key, value) {
  const idx = this.#index(key);                  // 1. 칸 번호 계산
  let node = this.#buckets[idx];
  while (node !== null) {                        // 2. 체인을 따라가며 같은 키 찾기
    if (node.key === key) { node.value = value; return false; }   // 있으면 덮어쓰기
    node = node.next;
  }
  this.#buckets[idx] = new Node(key, value, this.#buckets[idx]); // 3. 없으면 체인 맨 앞에 삽입 O(1)
  this.#size++;
  if (this.#size / this.#capacity > MAX_LOAD_FACTOR)             // 4. 적재율 초과면 확장
    this.#resize(this.#capacity * 2);
  return true;
}
```

- `get` : 칸 계산 → 체인 순회하며 키 비교 → 값 또는 `undefined`
- `delete` : 칸 계산 → 체인에서 노드 제거(머리/중간/꼬리 모두 처리) → 너무 비면 축소
- `resize` : 모든 노드를 새 배열로 **재배치(rehash)**. O(n) 이지만 2배씩 늘리므로 **분할 상환 O(1)**

**말할 것**
- "새 노드를 체인 **맨 앞**에 넣는 이유는 끝까지 안 가도 되기 때문입니다. O(1)입니다."
- "리사이즈 한 번은 O(n)이지만 2배씩 늘리니, 전체로 나누면 한 번의 `set`당 평균 O(1)입니다."
- 증거: "무작위로 저장·삭제·조회를 5만 번 하면서 내장 `Map`과 결과를 비교하는 테스트를 만들었습니다. 한 번도 다르지 않았습니다."

**예상 질문**
- *리사이즈 중에 서버가 멈추지 않나요?* → 멈춥니다. 한 번에 전체를 재배치하기 때문입니다. 실제 Redis는 증분(incremental) 리해싱으로 나눠 처리하는데, 이건 한계로 인정하고 개선 과제로 남겼습니다.

## 슬라이드 6. 동시성 ⭐

**화면에 띄울 것**

**없으면 생기는 문제 — 갱신 유실 (INCR 예)**

```
요청 A: 값 읽음 (10)
요청 B: 값 읽음 (10)      ← A 가 쓰기 전에 읽음
요청 A: 11 을 씀
요청 B: 11 을 씀          ← 12 여야 하는데 11. 한 번의 증가가 사라짐
```

**해결: 단일 스레드 + 모든 명령이 `await` 없는 동기 함수**

```
  네트워크 (비동기, 요청이 동시에 도착)
      │ 본문 수신 완료
      ▼
  ┌──────────────────────────────┐
  │ store.incr('counter')         │  ← 이 안에서는 다른 요청이 절대 끼어들 수 없음
  │ 읽기 → +1 → 쓰기 → AOF 기록   │
  └──────────────────────────────┘
      ▼
  응답 전송 (비동기)
```

**증거 (테스트)**
- 동시 `INCR` 500개 → 정확히 **500** (반환값 1~500 전부 유일)
- 동시 `SET NX` 100개 → 정확히 **1명만** 성공 (분산 락 패턴)
- 같은 키에 PUT·GET·DELETE 를 섞어 300라운드 → 찢어진(torn) 값 없음

**말할 것**
- "Node.js 이벤트 루프는 한 번에 콜백 하나만 실행합니다. 그래서 명령이 `await` 없이 끝까지 실행되면, 실행 도중에 다른 요청이 끼어들 수 없습니다. **락이 필요 없습니다.**"
- "진짜 Redis도 같은 모델입니다. 단일 스레드라서 빠른 게 아니라, 단일 스레드라서 **단순하고 안전**한 겁니다."
- "저장할 때 값을 복사하는 것도 같은 이유입니다. 호출자가 나중에 객체를 수정해도 저장소 내부가 오염되지 않습니다."

**예상 질문**
- *CPU 코어를 하나만 쓰는 건 단점 아닌가요?* → 맞습니다. 확장하려면 키 해시로 샤딩한 여러 프로세스가 필요합니다. 또 명령 하나가 오래 걸리면 모든 요청이 기다립니다. 그래서 배치 크기에 상한을 두었습니다.
- *"읽고 → 판단하고 → 쓰기"는 안전한가요?* → 두 요청에 걸치면 안전하지 않습니다. `incr`, `SET NX` 처럼 한 명령으로 끝나는 연산을 써야 합니다.

## 슬라이드 7. 만료 처리 ⭐

**화면에 띄울 것**

**없으면 생기는 문제**
- 낡은 데이터가 **영원히** 응답된다
- 한 번 쓰고 안 읽는 키가 쌓여 **메모리 누수**
- "5분만 유효한 락" 같은 임시 키를 만들 수 없다

**해결: 두 가지 전략을 함께 사용 (Redis와 동일)**

| | Lazy expiration | Active expiration |
|---|---|---|
| 언제 | 키에 **접근할 때** | **1초마다** 주기적으로 |
| 동작 | 만료됐으면 그 자리에서 삭제하고 "없음"(404) | 해시 테이블을 200개씩 훑어 만료 키 삭제 |
| 막는 문제 | **만료된 값이 응답으로 나가는 것** | **아무도 안 읽는 키가 메모리에 남는 것** |

```js
#live(key) {                                   // 모든 접근 경로가 이 함수를 거친다
  const entry = this.#table.get(key);
  if (entry === undefined) return undefined;
  if (this.#isExpired(entry, this.#now())) {   // expiresAt <= 지금
    this.#remove(key, entry);                  // 그 자리에서 삭제
    return undefined;                          // → "없음"
  }
  return entry;
}
```

**말할 것**
- "**요청받은 값이 만료됐다면?** 지우고 없는 것처럼 답합니다. `get` 뿐 아니라 `exists`, `ttl`, `incr`, `SET NX` 판정까지 모든 경로가 `#live`를 거치므로 만료된 값이 새어 나갈 수 없습니다."
- "Lazy만 쓰면 아무도 안 읽는 키가 영원히 남습니다. 그래서 1초마다 조금씩 훑는 청소부(active)를 같이 둡니다. 한 번에 전체를 보지 않고 200개씩 보는 건, 단일 스레드라서 오래 걸리면 모두가 기다리기 때문입니다."
- "만료 시각을 '60초 뒤'가 아니라 **절대 시각**으로 저장합니다. 이유는 AOF 슬라이드에서 나옵니다."
- 증거: "시계를 직접 조작하는 가짜 시계를 주입해서 정확히 만료 시각(경계값)에서 만료되는지 테스트했습니다. HTTP 테스트에서도 만료 후 요청하면 404입니다."

## 슬라이드 8. 무효화 ⭐

**화면에 띄울 것**

**없으면 생기는 문제**
- TTL 만 쓰면 **TTL 이 끝날 때까지 낡은 값이 나간다.** 가격을 수정해도 최대 60초간 옛 가격이 응답됨
- 관련 키를 한꺼번에 지우기 어렵다 (카테고리 상품 캐시 수백 개를 하나씩 `DEL`?)

**해결: 원본이 바뀌면 즉시 폐기**

| 기준 | 요청 | 비용 |
|---|---|---|
| `key` | `{"key":"product:7"}` | O(1) |
| `tag` | `{"tag":"category:c1"}` | O(해당 키 수) |
| `prefix` | `{"prefix":"product:"}` | O(n) |
| `all` | `{"all":true}` | O(n) |

```
PUT product:1 {tags:["category:c1"]}      tagIndex:  "category:c1" → { product:1, product:6 }
PUT product:6 {tags:["category:c1"]}
POST /invalidate {"tag":"category:c1"}  →  tagIndex 에서 키 집합을 바로 꺼내 그 키들만 삭제
```

| | TTL | 무효화 |
|---|---|---|
| 폐기 시점 | 시간이 지나서 (자연스럽게) | 이벤트가 발생해서 (즉시) |

**말할 것**
- "`DEL`은 키 하나를 지우는 겁니다. **무효화는 '원본이 바뀌어서 믿을 수 없게 된 캐시를 기준 단위로 한 번에 폐기'** 하는 겁니다."
- "태그는 Redis에는 없고 제가 추가한 기능입니다. 저장할 때 태그를 붙여 두면 `태그 → 키 집합` 보조 인덱스로, 전체를 훑지 않고 그 그룹만 지웁니다."
- "안전장치로 기준은 **정확히 하나만** 받습니다. `{key, tag}`를 같이 보내면 400입니다. 실수로 범위가 넓어지는 걸 막기 위해서입니다."
- "TTL과 무효화는 같이 쓰라고 권합니다. 무효화 호출이 어딘가에서 빠져도 **TTL이 최후의 안전망**이 됩니다."
- 증거: "무효화 직후 같은 키를 조회하면 반드시 404인지 50번 반복 검증했습니다. 데모에서는 상품 가격을 수정하면 캐시가 폐기되고 새 가격이 나옵니다."

## 슬라이드 9. AOF — 서버가 죽어도 (Optional)

**화면에 띄울 것**

**없으면 생기는 문제**
- 재시작하면 데이터가 **전부 사라진다** (메모리는 휘발성)
- **콜드 스타트 폭풍**: 캐시가 갑자기 비면 모든 요청이 DB 로 몰려 DB 가 쓰러질 수 있다 — 캐시가 DB 를 보호하다가 반대로 장애의 방아쇠가 됨

**해결: 변경 명령을 로그 끝에 계속 덧붙이고, 재시작 시 처음부터 재생**

```
{"o":"p","k":"user:1","v":{"name":"kim"},"e":1789000000000,"t":["user"]}   저장
{"o":"d","k":"user:1"}                                                    삭제
```

| 문제 | 대응 |
|---|---|
| 꺼져 있던 동안 만료된 키가 되살아남 | 만료 시각을 **절대 시각**으로 저장 → 복원 시 이미 지났으면 복원하지 않음 |
| 쓰다 만 마지막 줄 (전원 차단) | 버리고 파일을 잘라냄 |
| 중간에 깨진 줄 | 그 줄만 건너뛰고 나머지 복구 |
| 로그가 계속 커짐 | **compaction**: 살아있는 키만 임시 파일에 쓰고 `rename` 으로 원자적 교체 |
| fsync 비용 | `always` / `everysec`(기본) / `no` 선택 |

**말할 것**
- "write와 '디스크에 박혔다'는 다릅니다. write는 OS 캐시로 가고 fsync가 디스크로 내립니다. 기본인 `everysec`은 OS가 죽으면 최대 1초 분량을 잃을 수 있고, `always`는 안전하지만 느립니다."
- "프로세스만 죽는 경우(`kill -9`)는 이미 write된 데이터가 OS 캐시에 있어서 어느 정책이든 보존됩니다. 실제로 `SIGKILL` 후 복구되는지 테스트했습니다."
- "compaction은 `rename`이 원자적이라는 점을 씁니다. 도중에 죽어도 옛 파일이 그대로 남습니다."

**예상 질문**
- *RDB 스냅샷은 왜 안 했나요?* → AOF 쪽이 데이터 손실이 적고 구현이 직관적이라 먼저 했습니다. 스냅샷은 복구가 빠른 장점이 있어 개선 과제입니다.
- *AOF 쓰기가 동기 I/O 아닌가요?* → 맞습니다. 이벤트 루프를 잠깐 막지만, 대신 실행 순서 = 로그 순서가 보장되고 단순합니다. 한계로 인정합니다.

## 슬라이드 10. ⏩ LRU 축출

**화면에 띄울 것**

**없으면 생기는 문제**
- 상한이 없으면 메모리가 계속 늘어 **OOM**
- 상한만 있고 축출이 없으면 가득 찬 순간부터 **새 키가 전부 거부**되고, 옛 데이터가 자리를 차지 → 적중률 하락

**해결: 해시 테이블 + 이중 연결 리스트**

```
해시 테이블   key ──▶ entry                      찾기 O(1)
이중 연결 리스트   head ⇄ entry ⇄ entry ⇄ tail      순서 갱신/제거 O(1)
                 (최근)                 (가장 오래됨 = 축출 대상)
```

**말할 것**
- "해시 테이블만 있으면 '가장 오래된 것'을 찾으려 전체를 훑어야 하고, 리스트만 있으면 키를 찾으려 훑어야 합니다. 둘을 합치면 모두 O(1)입니다."
- "가득 차면 만료된 키부터 정리하고, 그래도 가득일 때만 tail을 버립니다. `EVICTION=lru MAX_KEYS=1000`으로 켜고, 기본은 기존 동작(`noeviction`)입니다."

## 슬라이드 11. ⏩ 배치 · SCAN · 트랜잭션

**화면에 띄울 것**

| 기능 | 없으면 | 해결 | 증거 |
|---|---|---|---|
| `mget` / `mset` | 키 N개에 요청 N번 | 한 요청 + 한 번의 동기 실행. `mset`은 **전부 저장 or 전부 거부** | 키 1,000개 읽기 76ms → **2.3ms** |

- "AOF에는 트랜잭션을 **한 줄**로 기록합니다. 쓰다 만 줄은 통째로 버려지므로 크래시가 나도 절반만 복구되지 않습니다."
- 자세한 내용은 [batch-scan-transaction.md](./batch-scan-transaction.md)

## 슬라이드 13. 성능 비교 — 캐시 사용 vs 미사용 ⭐

**화면에 띄울 것**

조건: 요청 3,000건 · 동시 50 · DB 쿼리 50ms(커넥션 풀 10개) · 상품 200종, 인기 상품에 쏠린 분포 · 실제 HTTP 통신

| | 캐시 없음 | 캐시 (cold) | 캐시 (warm) |
|---|---|---|---|
| 처리량 (req/s) | 160 | 1,942 | **5,474** |
| 평균 지연 (ms) | 310.5 | 25.7 | **9.1** |
| p95 (ms) | 315.8 | 171.8 | 13.9 |
| DB 쿼리 수 | 3,000 | 200 | **0** |

→ 속도 향상: cold **12.1배**, warm **34.2배**

**말할 것**
- "캐시가 없을 때 처리량 160 req/s는 DB 한계(`풀 10개 ÷ 50ms = 200 req/s`)에 그대로 묶인 값입니다. 캐시가 이 병목을 없앱니다."
- "cold는 빈 캐시에서 시작한 값이고 warm은 채워진 뒤입니다. cold의 p95가 높은 건 시작 직후 miss가 몰려서 DB 풀 대기가 생기기 때문입니다."
- "DB 쿼리가 3,000 → 200으로 줄었습니다. 200은 상품 종류 수입니다. 상품마다 **처음 한 번만** DB를 조회하고, 그 순간 같은 상품에 동시 miss가 나도 `getOrSet`의 single-flight가 **하나로 합쳐** 줍니다."
- ⚠️ **정직하게:** "이건 'DB가 느린 상황'을 가정한 시뮬레이션입니다. 원본이 1ms 미만으로 빠르면 이득이 작거나 없을 수 있습니다. `LATENCY_MS=1 npm run bench`로 직접 확인해 볼 수 있습니다. 절대값은 머신마다 다릅니다."

**캐시 클라이언트가 처리하는 엣지 케이스**
- **cache stampede**: 같은 키의 동시 miss → loader 는 1번만 (single-flight)
- **fail-open**: 캐시 서버가 죽거나 응답이 없어도 loader 결과로 정상 응답
- **negative caching**: 없는 id 도 짧게 캐시 → 반복 조회로 DB 가 뚫리는 것 방지
- loader 에러는 캐시하지 않음

## 슬라이드 14. 라이브 데모

**준비:** 터미널 1에서 `npm run demo` (Mini Redis 6380 · 캐시 API 4000 · 캐시 없는 API 4001)

> Windows PowerShell 에서는 `curl` 이 아니라 **`curl.exe`** 를 쓰세요. JSON 은 작은따옴표로 감싸고 안쪽 따옴표를 `\"` 로 씁니다.

```powershell
# 1) MISS → HIT : 캐시 효과
curl.exe -s -o NUL -w "%{time_total}s\n" localhost:4000/products/2     # MISS  ≈ 0.13s
curl.exe -s -o NUL -w "%{time_total}s\n" localhost:4000/products/2     # HIT   ≈ 0.002s
curl.exe -s -o NUL -w "%{time_total}s\n" localhost:4001/products/2     # 캐시 없음 ≈ 0.11s

# 2) 무효화 : 원본을 바꾸면 캐시가 폐기되고 새 값이 나온다
curl.exe -X PUT localhost:4000/products/1 -H "content-type: application/json" -d '{\"price\":999}'
curl.exe -i localhost:4000/products/1                                  # X-Cache: MISS, price: 999
curl.exe -i localhost:4000/products/1                                  # X-Cache: HIT

# 3) 내부 상태 : TTL 이 줄어드는 것, 해시 테이블 상태
curl.exe localhost:6380/keys/product:1                                 # ttlMs 가 60000 에서 줄어듦
curl.exe localhost:6380/stats                                          # hit/miss, table.capacity, longestChain

# 4) 태그 무효화
curl.exe localhost:4000/products/6
curl.exe localhost:4000/products/11
curl.exe -X DELETE localhost:4000/cache/category/c1                    # {"invalidated":3}
```

**(시간 되면) 재시작 복구:** 데모를 `Ctrl+C` 로 끄고 `npm run demo` 재실행 → `curl.exe -i localhost:4000/products/2` → `X-Cache: HIT` (60초 안이라면). 시작 로그의 `AOF restored: N keys` 도 보여 주기.

**말할 것**
- "첫 요청은 DB를 거쳐서 0.13초, 두 번째는 캐시에서 0.002초입니다. 약 **50배** 차이입니다. 응답 본문은 세 경우 모두 같습니다 — 캐시를 써도 결과는 안 바뀌고 속도만 바뀝니다."

## 슬라이드 15. 한계와 개선 아이디어

**화면에 띄울 것**

| 한계 | 개선 방향 |
|---|---|
| 리사이즈가 **한 번에 전체 rehash** → 키가 수백만이면 순간 멈춤 | 증분(incremental) rehash (Redis 방식) |
| AOF 쓰기·compaction 이 **동기 I/O** | 쓰기 큐 + 워커, compaction 을 worker thread 로 |
| **단일 코어**, 복제 없음 → 서버가 죽으면 복구될 때까지 중단 | 샤딩, 복제 |
| 트랜잭션에 **롤백·`WATCH` 없음** | 낙관적 락 |
| `MAX_KEYS` 는 키 **개수** 기준, 바이트 크기 무시 | `maxmemory` 바이트 단위, LFU 등 |
| HTTP 라서 `redis-cli`·기존 Redis 클라이언트로 접속 불가 | RESP 프로토콜(TCP) |
| 읽기 순서가 AOF 에 안 남아 재시작 직후 LRU 순서 부정확 | 스냅샷에 순서 포함 |

**말할 것**
- "한계를 알고 있다는 게 중요하다고 생각해서 README에 그대로 적어 두었습니다."

## 슬라이드 16. 정리

**화면에 띄울 것**

| 기능 | 없으면 | 해결 |
|---|---|---|
| 해시 테이블 | 키 조회가 O(n) | 해시 + 체이닝 + 리사이즈 → 평균 O(1) |
| 동시성 | 갱신 유실, 락 중복 획득 | 단일 스레드 + 동기(원자적) 명령 |
| 만료 | 낡은 값 영구 응답, 메모리 누수 | lazy + active expiration |
| 무효화 | 원본이 바뀌어도 낡은 캐시 응답 | key / tag / prefix / all 즉시 폐기 |
| AOF | 재시작하면 전부 소실, DB 로 폭주 | 로그 재생 + compaction |
| LRU | OOM 또는 새 키 거부 | 해시 + 이중 연결 리스트 |

**말할 것**
- "모든 기능은 같은 질문에서 나왔습니다. **'이게 없으면 무슨 문제가 생기지?'** 그리고 그 문제를 테스트로 재현하고, 해결된 걸 수치로 확인했습니다. 감사합니다."
